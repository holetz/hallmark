## Problem

The catalog MCP needs an index of metadata with lineage and code references; it can be built on a lightweight generator or on an existing catalog such as OpenMetadata or DataHub. Compare both on index freshness, code-link support, connectors and operating cost, and decide.

Member S18 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A written build-vs-adopt decision for the catalog engine, with the evidence behind each axis cited from a public source read on 2026-10-25: index freshness, code-link support, connectors, operating cost (RAM, disk, services).
- Three options compared on those four axes: a lightweight generator over a local SQLite index, OpenMetadata, and DataHub. OpenMetadata and DataHub are judged from their documentation, licenses, published sizing and APIs; neither is run and no image is pulled.
- A small prototype of the lightweight option in `spikes/catalog-engine/prototype/`, on synthetic metadata only: it builds a SQLite index (tables, columns, lineage edges, FTS5 search), links columns to `file:line` of source code, refreshes incrementally, and reports its own footprint.
- The decision recorded in `## Outcome` and a concrete proposal for the forge epic parked in `## Discoveries` (what S19 builds, which seam keeps adoption possible later).

## Out of Scope

- Running, installing or benchmarking OpenMetadata or DataHub, or pulling any image: the owner ruled it out for this spike; their cost is judged from published requirements only.
- Any call to Databricks or to a paid model: the prototype reads a synthetic JSON fixture, never a workspace.
- The production Unity Catalog connector, the MCP surface and semantic search: S19 (`holetz/hallmark#2`) builds them; the spike only proves the index shape and the code-link idea.
- Decisions about the model, job or data-quality MCPs (S22, S23).
- Real catalog, schema, table, host, token or e-mail names: the repository is public and the fixture uses obviously synthetic names only.

- `python3 -m unittest discover -s spikes/catalog-engine/prototype -p test_index.py` exits 0: the index builds from the fixture, a column resolves to the expected `file:line` hits, a second refresh with one changed table rewrites only that table, and the FTS search finds a column by a description word.

### Decisions

**D1. The decision is made from published evidence, not from running the tools.** Resource requirements come from each project's own deployment docs and compose files; license from the repository LICENSE; connector coverage from the connector catalogue; freshness from the ingestion model each documents. A claim whose page does not state it is written as "not found in the pages read", never as absent.

**D2. The lightweight prototype is SQLite with FTS5, stdlib only.** No server, no extra process, one file; the connector seam is a function returning a plain snapshot dict (tables, columns, lineage edges, `last_altered`), so a Unity Catalog connector and the synthetic fixture are interchangeable. Alternatives weighed: DuckDB (needs a dependency, no gain at this size) and plain JSON files (no search, no join between lineage and code links).

**D3. Code links are a first-class table, not a tag.** `code_ref(column_fqn, path, line, kind, snippet)` is filled by a scanner that matches a fully-qualified column or `table.column` token in source files and records the line. This is the capability the epic names as hallmark's reason to exist and the one neither catalog documents natively (D1 caveat applies).

**D4. Freshness is incremental by `last_altered`.** The refresh compares each table's `last_altered` against the stored value and rewrites only changed tables, which is what a scheduled job can afford. Lineage in `system.access.table_lineage` and `column_lineage` keeps a rolling one-year window, so the index must persist the edges it has seen (Databricks lineage system-tables page, "Data retention").

**D5. Contracts the design must not contradict.** Epic Design: "hallmark answers from a local index; only the job that refreshes the index talks to Unity Catalog and the other sources, through the proxy." Public repository: synthetic names only. Reference licenses: Apache-2.0 projects may be reused with attribution; nothing is vendored in this spike.

## Alternatives Considered

- **Adopt OpenMetadata as the engine.** Rejected as the default: the published minimum for one deployment is 2 vCPU / 4 GB for the server plus a separate OpenSearch/Elasticsearch (2 vCPU / 2 GB, 30 GB disk) and a MySQL/Postgres (2 vCPU / 2 GB, 30 GB disk), and the managed ingestion runs on Airflow, so a laptop profile (S13) and the 30-session server (S14) both gain three to four more services. Its Databricks and MLflow connectors are real strengths.
- **Adopt DataHub as the engine.** Rejected as the default: the quickstart compose runs GMS, frontend, actions, Kafka, MySQL and OpenSearch plus an upgrade job, with a tested floor of 2 CPUs, 8 GB RAM, 2 GB swap and 13 GB disk. Streaming-first Kafka updates and column-level Databricks lineage are real strengths.
- **Hybrid: lightweight index now, export to a catalog later.** This is the recommendation in `## Outcome`: it is the same decision as building, with the connector/snapshot seam kept clean so a later DataHub or OpenMetadata sink is an adapter, not a rewrite.
- **Do nothing and let agents query Unity Catalog directly.** Rejected by the epic: the agent loses the table/column to file-and-line link, which H4 (S20) measures.

## Open Decisions

- Semantic search backend (local embeddings vs FTS5 only): decided in S19 by measuring recall on the H4 question set; the prototype ships FTS5 only.
- Whether S19 keeps SQLite or moves to a service store if the index passes one million columns: decided by the prototype's `--bench` numbers extrapolated in `## Outcome`, revisited only if S19 meets that scale.
- The `verification` policy stays at the default (`per-section`): no human chose otherwise.

## Risks

- A catalog's capability is misread from its docs because a page omits a feature. Mitigation: absence claims are worded "not found in the pages read", with the page URL, and the decision carries a confidence level.
- Synthetic fixture shapes hide real-catalog complexity (nested types, thousands of schemas, tags). ACCEPTED — the spike proves the index shape and the code-link idea; S19 tests against the real connector.
- The prototype's footprint numbers are mistaken for production numbers. Mitigation: `## Outcome` labels them as generated-fixture numbers on one developer machine.
- A fixture or note leaks a real name into a public repository. Mitigation: synthetic names only, and `bash scripts/verify_repo.sh` plus the pre-commit leak hook run before each commit.
