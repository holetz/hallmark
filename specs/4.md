## Problem

Model engineers and monitoring scientists ask agents about model versions, experiments and stability, which today means clicking through MLflow. Expose the MLflow registry, versions and experiments, performance and stability metrics, drift and monitoring alerts over MCP, read-only for promotion and training.

Formerly holetz/assay#1.

Member S22 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A second read-only stdio MCP server, `python3 -m hallmark models-serve`, answers model questions live from an MLflow-shaped REST API (registry, versions, experiments, runs, metric history).
- Eight tools exist: `list_models`, `get_model`, `list_experiments`, `list_runs`, `get_run`, `metric_history`, `performance`, `drift`; every list is capped at 50 and reports `truncated`.
- `performance` compares the metrics of a model's versions side by side and reports stability (min, max, mean, spread, last) of a metric over its history.
- `drift` reports drift and monitoring metrics of a model version against thresholds and returns alerts, with the metric-naming convention stated in the tool description.
- Nothing can promote, stage, train, delete or write: the client allows only GET plus the two MLflow search POSTs, and a test proves any other path is refused.
- Tests run offline against a synthetic MLflow-shaped fixture, through a stub client and through a local `http.server` bound to 127.0.0.1; the repository gate stays green.

## Out of Scope

- Promoting, transitioning, tagging, deleting or training anything: the epic forbids it without approval, so the client has no write path at all.
- Indexing models into the local SQLite catalog: the catalog already lists Unity Catalog models; this server answers about metrics and runs, which change faster than a refresh job.
- Running or installing a real MLflow, and any Databricks call: tests use fixtures only.
- Computing drift from raw data: the server reads drift metrics a monitoring job already logged; it never touches table data.
- Embeddings or free-text search over runs.

### Decisions

**D1. Live reads, not an index.** The server queries the MLflow REST API per call through an injected client. Alternative weighed: refresh models into the SQLite index like the catalog. Live wins because performance and drift metrics change after every run and a stale index would answer wrongly; the epic's "only the refresh job talks to sources" binds the catalog server (spec 2 D9), which this server is not, and it stays a separate process so `serve` still never opens a socket. Recommendation taken at high confidence.

**D2. Read-only by construction.** The client exposes `get(path, params)` and `search(path, body)`; `search` accepts only `experiments/search` and `runs/search`, the MLflow reads that are POST. Any other path raises before a request exists. The tool layer has no write tool to expose.

**D3. Standard library, reusing spec 2's patterns.** Hand-rolled newline JSON-RPC like `hallmark/mcp.py`, importing its helpers; a pure `handle(client, message)` so tests need no process; production client over `urllib` with bearer token from `HALLMARK_MLFLOW_HOST` / `HALLMARK_MLFLOW_TOKEN` (token optional for a local server), exercised with a stub opener and a localhost fixture only.

**D4. Stages and aliases both.** Classic registries expose `current_stage`; Unity Catalog registries expose aliases. Versions are reported with `stage` (may be empty) and `aliases`, and `performance` and `drift` default to the version carrying alias `champion`, else the highest version number.

**D5. Drift is a convention over logged metrics.** A metric is a drift metric when its key contains `drift`, `psi` or `ks_stat` (case-insensitive). The threshold is the run param `<key>.threshold` when present, else the call's `threshold` argument (default 0.2). A value above the threshold is an alert with `severity` `high` at twice the threshold, else `medium`. The convention is stated in the tool description and is an assumption confirmed against a real monitoring job (Open Decisions).

**D6. Bounded output.** `get_run` caps params and tags like any list; `metric_history` returns at most the requested `limit` points (latest first) plus a summary over the whole fetched history.

**D7. Contracts the design must not contradict.** Public repository: synthetic names only (`demo_*`), no hosts, tokens or e-mails; hooks never bypassed; no paid model call; Databricks never contacted.

## Alternatives Considered

- Index models into the SQLite catalog: rejected, stale for metrics (D1).
- The official MCP SDK or the real `mlflow` package as client: rejected, a heavy dependency for read-only REST of eight calls; spec 2 chose hand-rolled for the same reason.
- One merged server with the catalog tools: rejected, it would force `serve` to import a network client and break the offline guarantee.

## Open Decisions

- Drift naming convention (D5): decided against a live monitoring job when one is available; until then the tool description states it. Settled by the first live run.
- Whether a stage-less Unity Catalog registry also needs `latest_versions` fallback: decided by the first live run; the client tolerates both shapes now.
- Pagination ceiling for very large registries: kept at 20 pages of 100; revisit with real volume.

## Risks

- MLflow field names differ by version: the shapers tolerate missing optional fields and name a missing required one. Fixtures follow the documented 2.0 REST shape; confirmed in the first live run.
- A model with many versions makes `performance` issue one run read per version: capped at the 5 latest versions, reported as `truncated`.
- Silent write path: guarded by the allowlist test (D2). ACCEPTED — the production client cannot prove the server side is read-only, only that this process sends no write.
- Credential exposure: the token is read from the environment and never logged or put in an error message.
