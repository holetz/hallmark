## Problem

Data engineers ask agents why a pipeline failed or whether a table is fresh, which today means reading job runs by hand. Expose job and pipeline status, failures and reruns, data-quality results and alerts per table and pipeline over MCP, never triggering or changing a production job.

Formerly holetz/pyrometer#1.

Member S23 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A third read-only stdio MCP server, `python3 -m hallmark ops-serve`, answers data-operations questions live from a Databricks-shaped REST API (Jobs 2.1, Pipelines 2.0, SQL alerts 2.0), through an injected client.
- Nine tools exist: `list_jobs`, `job_status`, `list_failures`, `get_run`, `reruns`, `list_pipelines`, `pipeline_status`, `data_quality` and `alerts`; every list is capped at 50 and reports `truncated`.
- `list_failures` returns the failed, timed-out and internally-errored runs of a window, with the failed tasks and their state message; `reruns` reports retries (attempt number) and repairs (repair history) of a job's recent failed runs and the outcome of the last attempt.
- `data_quality` aggregates pipeline expectation results (passed and failed records) per table and expectation from the pipeline event log, and `alerts` lists SQL alerts with their state, filterable by a table or pipeline name.
- Nothing can run, rerun, repair, cancel, create, reset, update or delete anything: the client has no POST method at all and `get` accepts only an allowlist of read paths, so a write-shaped path is refused with `ReadOnlyError` before any request is built.
- Tests run offline against a synthetic fixture shaped like the Databricks Jobs API, through a stub client and a local `http.server` bound to 127.0.0.1; Databricks is never contacted; the repository gate stays green.
## Out of Scope

- Triggering, rerunning, repairing, cancelling, pausing or editing a job or a pipeline update: the epic forbids it, so the client has no write path. "Reruns" here means reading the history of retries and repairs that already happened.
- Compute, cluster and cost reads (those belong to the forge cost spec) and the job's source notebooks (the catalog server links code).
- Indexing runs into the local SQLite catalog: run state changes by the minute, so the server answers live (same reasoning as the models server).
- Lakehouse Monitoring tables and `system.*` SQL: they need a SQL warehouse, which is a different connector; data quality here is what the pipeline event log and SQL alerts expose over REST.

### Decisions

**D1. Live reads, not an index.** Same as the models server: run state and event logs change by the minute; a separate process keeps `serve` offline.

**D2. Read-only by construction, stricter than the models client.** `DatabricksClient` has a single transport method, `get(path, params)`, and no body-sending method, because every read this server needs is a GET in the Jobs, Pipelines and SQL-alerts APIs. `get` matches the path against a closed allowlist of full patterns (`/api/2.1/jobs/list|get`, `/api/2.1/jobs/runs/list|get|get-output`, `/api/2.0/pipelines`, `/api/2.0/pipelines/<id>`, `/api/2.0/pipelines/<id>/events|updates`, `/api/2.0/sql/alerts`); anything else, including every write verb of those APIs, raises `ReadOnlyError` before a request exists. The pipeline id is `[A-Za-z0-9_-]+` so it cannot smuggle a path segment.

**D3. Standard library, reusing the earlier patterns.** Hand-rolled newline JSON-RPC importing the helpers of `hallmark.mcp`, a pure `handle(client, message)`, an injected opener; host and token come from `HALLMARK_DBX_HOST` and `HALLMARK_DBX_TOKEN` (both required), never put in an error message.

**D4. Failure means a terminal bad state.** A run is a failure when `state.result_state` is `FAILED` or `TIMEDOUT`, or its `life_cycle_state` is `INTERNAL_ERROR`. `CANCELED` is reported separately as `canceled`, not counted as a failure. The window is `hours` (default 24, max 720) turned into `start_time_from` (milliseconds); the clock is a module function tests patch.

**D5. Reruns are read from run history.** `runs/list` carries `attempt_number` and `original_attempt_run_id` (retries); `runs/get` carries `repair_history` (entries typed `ORIGINAL` or `REPAIR`). `reruns(job_id)` looks at the job's latest failed runs (cap 10), reads each with `runs/get`, and reports `attempts`, `repairs` and the `last_result` (state of the latest repair entry, else of the run). Fields are read tolerantly; a missing optional one is omitted.

**D6. Data quality comes from expectations in the pipeline event log.** `data_quality(pipeline_id, table?)` reads `flow_progress` events whose `details.flow_progress.data_quality.expectations` list `{name, dataset, passed_records, failed_records}`, aggregates by `(dataset, name)` over the fetched events (up to 20 pages), and flags `alert: true` where `failed_records > 0`, with `pass_rate`. A table filter matches `dataset` exactly or as the suffix after the last dot. `alerts` reads SQL alerts and returns `display_name`, `state`, `lifecycle_state` and `update_time`, filtered by a case-insensitive name substring and optionally by state; the owner field is deliberately not returned.

**D7. Bounded output.** Error text and traces are truncated to 2000 characters per field; task lists are capped by `limit`; pagination follows `next_page_token` with a 20-page ceiling.

**D8. Contracts the design must not contradict.** Public repository: synthetic names only (`demo_*`), reserved example hosts, no tokens or e-mails; hooks never bypassed; no paid model call; Databricks never contacted.
## Alternatives Considered

- Index runs into the SQLite catalog: rejected, stale within minutes (D1).
- A client with `post` limited to read POSTs, as MLflow needed: rejected, none of the Jobs, Pipelines or alerts reads needs a POST, so the strictest client (GET only) is available and a test can assert no body-sending method exists.
- Use the Databricks SDK or managed MCP: rejected, a heavy dependency and the epic says not to repeat what the managed MCP already serves; this server answers the cross-cutting questions (failures, reruns, expectation results) in one place and stays auditable in one allowlist.
- Read quality from `system.*` tables or Lakehouse Monitoring over SQL: rejected for now, needs a warehouse connector (Out of Scope).

## Open Decisions

- Field names of the real Jobs 2.1, Pipelines and SQL alerts responses (notably `repair_history`, `expectations` and the new `/sql/alerts` shape versus the legacy `/preview/sql/alerts`): the fixtures follow the documented shape and the shapers tolerate missing optional fields; confirmed by the first live run.
- Whether "failure" should include `CANCELED` (D4): kept separate until a data team states how it reads cancellations.
- Pagination ceiling for very large workspaces: 20 pages; revisit with real volume.
- Pipeline event filtering by table uses the `dataset` name from expectations; whether a team labels quality by another key is decided by the first live run.

## Risks

- API field names differ by version: shapers are tolerant and the fixture follows the documented shape; confirmed in the first live run.
- `reruns` issues one `runs/get` per failed run: capped at 10 and reported `truncated`.
- Silent write path: guarded by the closed allowlist and by the test that no body-sending method exists. ACCEPTED — the process cannot prove the server side is read-only, only that it sends no write.
- Credential exposure: token read from the environment, never logged or placed in an error message; error traces are truncated and may still carry data a job printed (documented in the README).
- Public leak: fixtures use `demo_*` names and `.example.invalid` hosts; the leak gate runs.
