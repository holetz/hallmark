## Problem

hallmark is public and is built next to an adopter's real Databricks environment, so a catalog name, a workspace host, an author email or an absolute home path can reach the repository or its spec store, and nothing stops it today: the only protection is an interim hook outside the repository (`core.hooksPath` set by hand on 2026-10-24). Adopt the leak gate quenching ships (`holetz/quenching#2097`, modelled on bricksmith's ADR 0003): generic patterns built in, a private denylist outside the repository that fails closed, `pre-commit` and `pre-push` hooks that also check the author and committer email, and CI running the generic patterns plus gitleaks. The human asked for this protection in every repository of the project on 2026-10-24, which authorizes the hooks and the CI step.

## Proposal

- Every commit made in a clone that installed the hooks is refused when its staged content or author email leaks, through `scripts/githooks/pre-commit` calling the installed `cq security leak --staged`.
- Every push is refused when a pushed commit leaks (added lines, messages, author and committer emails), through `scripts/githooks/pre-push`.
- Both hooks fail closed: without `cq` on the PATH, or without the private denylist, the commit or push is refused.
- `bash scripts/verify_repo.sh` exists as the single repository gate: shell syntax, the hook behaviour test (where `cq` is installed) and the generic pattern scan.
- Pull requests and pushes to `main` run that gate plus gitleaks over the history in `.github/workflows/ci.yml`, with every action pinned by commit SHA and the narrowest permissions.
- `CONTRIBUTING.md` tells a contributor how to install the hooks (`git config core.hooksPath scripts/githooks`) and where the private denylist lives.

## Out of Scope

- Running `git config core.hooksPath` for anyone: it changes a clone's own configuration, so it stays a documented human step.
- Vendoring the leak engine or the private denylist: the engine is `cq security leak` of the quenching plugin, the denylist stays at `~/.config/quenching/denylist.txt`.
- Scanning the `quenching` specs-store branch in CI: it is a data branch and triggers nothing.
- Application code, tests of the MCP server and any build pipeline: hallmark has none yet.

## Validation

- `bash scripts/verify_repo.sh` exits 0 and ends with `verify_repo: green`.
- `bash scripts/test-leak-gate.sh` exits 0 and prints `ok` for: clean commit accepted, staged CPF refused, absent denylist refused, missing `cq` refused, clean push accepted, push carrying a CPF refused. It uses a temp denylist through `QUENCHING_DENYLIST_FILE`; the real denylist is never read.
- `bash scripts/leak-generic.sh` exits 0 on the tree and prints `leak-generic: clean`.
- `.github/workflows/ci.yml` parses as YAML, pins both actions to the SHAs of `actions/checkout` v7.0.1 and `gitleaks/gitleaks-action` v3.0.0, and grants `pull-requests: read` only to the gitleaks job.

## Design

Mirrors holetz/forge PR #18 (spec forge#13): same file layout and the same behaviour, adapted to what hallmark has (only `README.md`, `LICENSE` and the specs-store config today, so nothing existing is duplicated).

- **Hooks delegate to `cq security leak`.** Durable rule: the engine lives in the quenching plugin; the repository carries two thin shell hooks and no pattern logic of its own, so the engine cannot drift from the plugin. Alternative weighed: a self-contained hook with embedded patterns; rejected because the private denylist and the email checks belong to `cq`.
- **Fail closed.** A missing `cq` exits 1 with a message pointing to `CONTRIBUTING.md`; a missing denylist is refused by `cq` itself.
- **`scripts/leak-generic.sh` is the CI-side subset.** CI has no `cq` and no denylist, so the script scans tracked files with `git grep` for the generic patterns (CPF, CNPJ, Azure Databricks host, Databricks PAT, classic cluster id, private key). It prints file:line and the pattern name, never the matched text. It mirrors `cq security leak --generic-only` and is kept aligned by hand.
- **One gate.** `scripts/verify_repo.sh` is the only entry point, run by humans and by CI. The hook behaviour test runs only where `cq` exists; CI skips it with a printed line.
- **The test never touches the real denylist.** `QUENCHING_DENYLIST_FILE` points to a temp file; sample secrets are assembled at run time so the test file matches no pattern itself.
- **CI.** Triggers on push to `main` and on pull requests, ignoring the `quenching` branch; workflow permission `contents: read`; only the gitleaks job adds `pull-requests: read`, because the action lists a PR's commits through the API. `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1` (v7.0.1) and `gitleaks/gitleaks-action@e0c47f4f8be36e29cdc102c57e68cb5cbf0e8d1e` (v3.0.0) are pinned by SHA; gitleaks checks out with `fetch-depth: 0`.
- The hooks must be committed with the executable bit.

### Mapa de dependências (2026-10-25)

- Nothing in the repository depends on the new files: the tree holds only `README.md`, `LICENSE` and `.claude/quenching.json`.
- `verify_repo.sh` depends on `test-leak-gate.sh`, `leak-generic.sh` and `scripts/githooks/*`; `test-leak-gate.sh` depends on both hooks and `leak-generic.sh`; `ci.yml` depends on `verify_repo.sh`; `CONTRIBUTING.md` references all of them.
- Orphan risk: renaming any script breaks `verify_repo.sh` and CI at once.

## Alternatives Considered

- A third-party pre-commit framework: rejected; it adds a dependency and cannot run `cq`'s email and denylist checks.
- Gitleaks alone in CI: rejected; it knows nothing of the project's private terms or Brazilian tax ids, which the generic script covers.
- Waiting for hallmark code to exist before adding the gate: rejected; the spec store and the README can already leak.

## Open Decisions

- none — the design is a mirror of forge#13, whose decisions were already settled and merged.

## Risks

- The generic pattern list in `leak-generic.sh` drifts from `cq security leak --generic-only`: ACCEPTED — the script header says to keep them aligned by hand, as in forge; CI is the weaker net and the hooks are the strong one.
- A contributor never installs the hooks: ACCEPTED — installation changes a clone's git config and stays a documented human step; CI covers the generic patterns regardless.
- The test script matches a pattern in its own text: mitigated by assembling the sample CPF at run time, and `leak-generic.sh` runs over the test file in the gate.
