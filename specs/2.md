## Problem

Models invent table and column names, and Unity Catalog does not say which file and line produce a column. Build the local index (catalogs, schemas, tables, columns, tags, lineage, models, features), the Unity Catalog connector, table/column ↔ source-code links and semantic search, served over MCP.

Member S19 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent). Spec 1 (the catalog-engine spike, merged) decided to BUILD on SQLite + FTS5 with a `code_ref` table, a plain snapshot dict as the connector contract and append-only lineage; this spec follows that decision and turns the prototype's shape into the product.

## Proposal

- A `hallmark` Python package (standard library only) holding a SQLite index of catalogs, schemas, tables, columns, tags, lineage, registered models and features, with incremental refresh by `last_altered` and append-only lineage.
- A snapshot contract (a plain dict, validated on entry) that every connector returns; a Unity Catalog connector that turns Unity Catalog REST responses and `information_schema` / `system.access` rows into that snapshot through an injected client, so it is built and tested only against synthetic fixtures.
- A code linker that records, for each column and table, the `file:line` where source code mentions it (qualified hits and bare candidates), efficient enough to scan a repository against tens of thousands of columns.
- Search over names, comments and tags on FTS5 with BM25 ranking, stemming, identifier splitting (`order_total` is found by "order total") and an OR fallback; no model call and no embedding.
- A read-only MCP server over stdio exposing search, table and column detail, code links, lineage walk, models and index status, with bounded output; a CLI with `refresh` and `serve`.
- The repository gate runs the new tests, and the README documents the commands.

## Out of Scope

- Any call to Databricks, any live workspace, host, token or cluster: the connector is proven on synthetic fixtures; the live run is a later human step.
- Embeddings, vector search or any model call (paid, or a large local model): recorded as an Open Decision with a recommendation, not built.
- Models, drift, job and data-quality MCPs (S22, S23), and repeating what Unity Catalog or Databricks' managed MCP already serve.
- Writing back to any catalog; the index and the MCP are read-only.
- A second non-Databricks connector, or a DataHub / OpenMetadata sink: the snapshot seam keeps them possible.
- Any change to the CI workflow or its grants (that would be `needs-human`; none is needed).
- Real catalog, schema, host, token or e-mail names: the repository is public and fixtures use obviously synthetic names.

### Decisions

**D1. Standard library only, one SQLite file.** No server, no dependency, no extra process (spec 1 decision). `sqlite3` with FTS5 is required; the package fails with a clear message when FTS5 is missing.

**D2. The connector contract is a snapshot dict.** `{"tables": [...], "models": [...], "features": [...], "lineage": [...]}`; a table carries `fqn`, `comment`, `last_altered`, `tags`, `columns` (each with `name`, `type`, `comment`, `tags`). `snapshot.validate` rejects a malformed snapshot before it touches the store. A connector is any callable returning that dict; the Unity Catalog connector and a JSON file are interchangeable.

**D3. The Unity Catalog connector takes two injected clients.** A REST client (`get(path, params) -> dict`) serves catalogs, schemas, tables-with-columns and registered models, following `next_page_token` pagination; a SQL client (`query(statement) -> list[dict]`) serves tags (`information_schema.table_tags`, `column_tags`) and lineage (`system.access.table_lineage`, `column_lineage`). Production clients (`urllib`, bearer token and host from environment variables, the SQL one over the statement-execution REST API) exist but are only exercised with stub transports. Fixtures are shaped like the documented responses; nothing is called.

**D4. Refresh is incremental by `last_altered`, plus a tag signature.** A table is rewritten when its `last_altered` or its tag signature changed (a tag edit does not alter the table). Vanished tables are dropped; lineage is only ever added (`first_seen`, `last_seen`), because `system.access` keeps a rolling one-year window.

**D5. The linker tokenises lines, not regex-per-column.** Each line is split into identifier tokens (dotted names kept whole, backticks stripped, case-insensitive); tokens are looked up in a name map. A dotted token whose qualifier matches the table (`tail`, `schema.tail` or the full name) is `qualified`; a bare column token in a file that also mentions the table is `bare`, a candidate only. Cost is linear in file size, not in columns times lines.

**D6. Search is FTS5/BM25 with identifier splitting.** One FTS table with `name`, `text` and `tags` columns weighted by `bm25`, `porter unicode61` tokenizer, identifiers indexed both whole and split (`order_total` also as "order total"). The query is sanitised into quoted prefix terms, AND first, OR fallback when nothing matches. This is the "semantic" level this spec ships; embeddings are an Open Decision.

**D7. MCP is a hand-rolled stdio JSON-RPC 2.0 loop.** Newline-delimited messages, `initialize`, `ping`, `tools/list`, `tools/call`; the dispatcher is a pure function so tests drive it without a process. The index is opened read-only (`mode=ro`). Every list tool takes a `limit` capped at 50 and reports `truncated`, so replies stay under the harness's MCP output ceiling. Alternative weighed: the official MCP SDK (a dependency and a moving API for four methods); revisit if the protocol surface grows.

**D8. Features are a snapshot list, derived by the connector from a table marker.** A feature entry is `{fqn, table_fqn, columns}`; the connector derives it from tables whose properties carry a feature-table marker. The marker name is an assumption taken from the fixture and is confirmed in the live run (Open Decisions).

**D9. Contracts the design must not contradict.** Epic Design: "hallmark answers from a local index; only the job that refreshes the index talks to Unity Catalog and the other sources, through the proxy" (so `serve` never opens a network socket and never imports the connector). Public repository: synthetic names only. Hooks: never `--no-verify`.

## Alternatives Considered

- **Adopt DataHub or OpenMetadata.** Settled by spec 1: rejected as the default for operating cost and the missing column-to-code link; the snapshot seam keeps an adapter possible.
- **Query Unity Catalog live from the MCP.** Rejected by the epic: the agent would lose the file-and-line link and the server would need workspace credentials.
- **Embeddings in this spec.** Rejected: needs a model call or a large local model, both ruled out here; see Open Decisions.
- **Extend the spike in place.** Rejected: spikes are a decision record; the product gets its own package and tests, and lifts what proved out.

## Open Decisions

- Real embeddings for semantic search. Recommendation: do not add them now. Ship FTS5/BM25 with stemming and identifier splitting, keep a small `Ranker` seam in `hallmark/search.py`, and let S20 (H4) measure recall on the real question set. If recall on paraphrase queries is the gap, add an optional embedding column computed at refresh time (never at query time) with a small CPU model, behind a flag, and re-check the 12 MB / 45 MB footprint. Decided by: the H4 recall numbers.
- The feature-table marker and the exact REST field names (`updated_at` units, `properties` keys, tag-table columns) are confirmed in the live human run; the fixtures encode the documented shapes. Decided by: the first live refresh against a non-production workspace.
- Whether SQLite stays the store beyond about one million columns: unchanged from spec 1, revisited only if that scale appears.
- `verification` stays `per-section` (default); no human chose otherwise.

## Risks

- Synthetic fixtures drift from the real Unity Catalog shapes. Mitigation: the connector isolates all shape knowledge in one module with a docstring of the fields it reads; the live run is an explicit later step; unknown or missing optional fields are tolerated, required ones raise a named error.
- Bare-hit candidates mislead an agent. Mitigation: `kind` is returned on every code reference and the tool descriptions say bare hits are candidates.
- The test step slows or breaks CI. Mitigation: tests are in-memory and small, run in seconds; the step is added to the single gate only after it passes locally.
- A fixture leaks a real-looking name into a public repository. Mitigation: obviously synthetic names (`demo_catalog`, `acme_*`); the leak gate and the pre-commit hook run on every commit; never `--no-verify`.
- Hand-rolled MCP drifts from the protocol. ACCEPTED — four methods over stdio are small; tests pin the message shapes, and moving to the SDK is a local change.
